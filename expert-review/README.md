# Экспертная оценка модели — локальный пилот

Рабочее приложение Codex: Flask, SQLite, обычный JavaScript, линейный BWM через SciPy. Исходные 8 блоков и 24 компетенции импортируются из `../model-content.json` при первом запуске. Приложение не редактирует исходный файл или ранее подготовленные HTML-отчёты.

Для постоянного сервера добавлены [инструкция и конфигурации развёртывания](deploy/README.md): Gunicorn, отдельный пользователь, постоянная база и ежедневные резервные копии. Локальная демоверсия запускается по инструкции ниже.

## Запуск

Из каталога `expert-review`:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python app.py
```

Откройте <http://127.0.0.1:8766>. Для другого локального порта: `REVIEW_PORT=8768 .venv/bin/python app.py`. Сервер слушает только loopback; приглашение с адресом `127.0.0.1` не работает с другого компьютера. Остановить сервер — Ctrl+C в его терминале.

Кабинет организатора: <http://127.0.0.1:8766/#admin>. Ключ создаётся в `.data/admin-access.txt`, доступен только владельцу файла. Он не включён в репозиторий и не показывается в журнале сервера. Откройте файл локально, скопируйте ключ в форму входа. Для смены ключа остановите приложение, замените содержимое файла и перезапустите; существующие административные сеансы также следует удалить из таблицы `sessions` перед повторным запуском.

## Проверка интерфейса

На главной странице нажмите **Попробовать демоверсию**. Каждый такой запуск создаёт отдельное демонстрационное исследование. Данные сохраняются на сервере, но не входят в кабинет реального исследования, статистику или экспорт. В демо используйте вымышленные данные. Для возвращения к текущему демо в том же браузере нажмите **Продолжить оценку**.

Реальная панель изначально пустая. Организатор создаёт приглашение по имени и email и самостоятельно передаёт персональную ссылку. Ссылка — секрет входа на 30 дней, а не подтверждение владения почтовым ящиком. Автоматической рассылки и email-верификации нет. Личность проверяет организатор при передаче ссылки. Повторное создание приглашения для того же email отзывает старые ссылки и сеансы этого эксперта.

Эксперт заполняет профиль и отмечает минимум две области опыта. Система назначает два блока: сначала с меньшим числом назначений по всей панели, при равенстве — случайно. Выбор выполняется в транзакции, сохраняется между входами. Обычно это 6 компетенций и 2 оценки полноты. Сохранение ответов автоматическое; при конфликте двух окон сервер отклоняет устаревшую запись. После отправки ответы доступны только для чтения.

На экране «Как оценивать» можно заменить неподходящий блок, указав причину. Замена доступна до отправки первого раунда, только на другой блок из отмеченных областей опыта. Исключённый блок не назначается снова. Его черновики сохраняются в архиве, но не входят в результаты. В кабинете организатора показаны назначенные, начатые и отправленные блоки по всей панели. Балансировка учитывает назначения; достаточность завершённых оценок контролирует организатор по таблице покрытия.

При обновлении существующих данных сохраняются все уже начатые блоки и весь объём ранее отправленных ответов. Поэтому у начавших старую анкету может остаться больше двух блоков; интерфейс объясняет это. Для новых экспертов всегда назначаются ровно два.

## Раунды и методика

В приложении есть раздел **Методология** с описанием протокола и ссылками на первичные источники. Ориентир пилота — 3–5 экспертов. При двух блоках на человека минимум для 8 оценок каждого блока — 32 завершивших эксперта при идеальном покрытии; отказы и ограничения экспертизы могут увеличить число. I-CVI 0,78 при минимум 8 содержательных ответах — проектный параметр, не универсальный стандарт. Наблюдаемость добавлена как отдельный прикладной критерий. Оценки карточек не валидируют автоматически все знания и умения внутри них.

1. Первый раунд: релевантность, ясность, наблюдаемость; полнота блока; замечания к пунктам. Все шкалы 1–4, отдельно «недостаточно опыта».
2. Организатор изучает распределения и замечания по всей панели. В статистику попадают только отправленные ответы. Для малых групп результаты предварительные. Высокая доля 3–4 не заменяет содержательного решения редактора.
3. В разделе **Раунды и версии** организатор выбирает спорные компетенции и при необходимости загружает полный JSON новой редакции с той же структурой. Для прежних компетенций сохраняются идентификаторы; для новых нужны новые ID. Изменённые и новые компетенции включаются автоматически. Удаления видны в предпросмотре и сохраняются в журнале перехода.
4. Обоснование редакции — обязательный текст. Укажите решения по конкретным компетенциям и причины; удалите узнаваемые детали из обратной связи. Исходные экспертные комментарии не рассылаются автоматически.
5. Открытие второго раунда закрывает первый. Участвуют завершившие первый раунд, только по компетенциям своих блоков. Если в их блоках нет повторных вопросов, повторный раунд не требуется, и ложная отправка пустого ответа не создаётся. Они видят прежнюю версию, собственные оценки и снимок распределений группы. Групповые данные скрыты при менее трёх завершённых назначенных ответах на конкретную компетенцию; это мера приватности, а не достаточность выборки. Неназначенные вопросы не считаются пропусками.
6. После второго раунда организатор фиксирует содержание и открывает отдельный BWM для завершивших содержательную оценку, включая тех, кому повторный раунд не требовался. BWM сохраняет сравнение всех восьми блоков; прохождение двух блоков само по себе не подтверждает способность к такому сравнению. Организатор согласует участие в этом отдельном этапе с экспертами широкого системного профиля. Два раунда — ограничение текущего протокола; третьего раунда и возврата фаз в интерфейсе нет. Минимальная техническая проверка наличия хотя бы одного ответа не означает методологической достаточности — организатор отвечает за покрытие панели.
7. BWM: 8 блоков, 13 уникальных сравнений, общая пара наиболее/наименее важного задаётся один раз. Допустима равная важность. Решается линейная задача Rezaei (2016). Максимальная невязка не называется коэффициентом согласованности; порог AHP 0,1 не используется. Предупреждения проверяют явные противоречия порядка, но не являются полной статистической проверкой согласованности. Ответы не исправляются автоматически.
8. Веса агрегируются равным арифметическим средним по версии; дополнительно показаны стандартное отклонение и диапазон. Они описывают приоритеты блоков, а не готовую систему баллов сотрудников. Индивидуальные суждения и результаты доступны в полном архиве JSON.

## Данные и резервирование

- `.data/review.sqlite3` — база: профили, приглашения с хешами и сохранёнными токенами для копирования организатором, версии, черновики, отправленные ответы, веса и журнал переходов.
- `.data/admin-access.txt` — локальный ключ организатора.
- `CSV` — ответы с идентификаторами экспертов, историческим контекстом (у новых участников пусто) и признаком отправки. Черновики явно помечены; при самостоятельном анализе фильтруйте `submitted=True`.
- `JSON` — полный исследовательский архив, включая профили, все версии, раунды, ответы, время отправки, расчёты BWM и решения о переходах. Ссылки приглашений, ключ и сеансы в экспорт не входят. Поля `payload`, `data`, `profile`, `result`, `feedback`, `targets` внутри архива содержат JSON-строки из базы.
- Выгрузки содержат персональные данные и предназначены организатору. Сроки хранения определяются перед запуском реальной панели.

Для резервной копии остановите сервер и скопируйте весь каталог `.data` в защищённое место. Для восстановления остановите сервер и замените `.data` сохранённой копией. JSON — аналитический архив, не автоматический формат восстановления базы.

## Проверки

```bash
.venv/bin/python -m unittest discover -s tests -v
node tests/browser.cjs
```

Браузерная проверка использует временную базу и отдельный порт 8767. Она не добавляет тестовых участников в рабочее исследование. Путь к Playwright задаётся переменной `PLAYWRIGHT_MODULE`, к Chromium — `CHROMIUM_PATH`; по умолчанию используются доступные на текущей машине пути. Скриншоты сохраняются в игнорируемом `test-artifacts/`.

## Граница текущей версии

Готов локальный пилот, а не публичное размещение. Для удалённых экспертов следующим шагом нужны согласованный адрес размещения, HTTPS, сервер приложений вместо встроенного Flask, настройка допустимого домена и проверка эксплуатационных условий, резервирования и порядка работы с персональными данными. Публикация и фактическая рассылка не выполнялись. Текущая защита рассчитана на локальный запуск: персональные ссылки, HttpOnly-сеансы, CSRF, проверка Origin, ограничение попыток входа, разграничение доступа и защита от перезаписи устаревшим черновиком.

Обновление 21 октября 2026: контекст оценки больше не запрашивается и не разделяет назначения, результаты или новые раунды обратной связи. Исторические поля и снимки уже открытых раундов сохраняются для воспроизводимости. Приложение установлено на VPS; публичный адрес и HTTPS ещё ожидают настройки.

Обновление 23 октября 2026: email при приглашении необязателен. Участник идентифицируется внутренним ID; одноимённые участники без почты не объединяются. Для переиздания без почты API принимает `expert_id`. В старом столбце email для таких участников хранится служебный идентификатор `no-email:…`, а интерфейс показывает пустой email. Полный JSON-архив сохраняет это служебное значение.

Кабинет организатора сохраняет действующие персональные ссылки и позволяет копировать их из списка участников. Ссылки доступны только организатору, не включаются в исследовательский экспорт. При создании приглашения можно заполнить организацию и должность; организатор и эксперт могут исправить эти поля. Предзаполнение не означает согласие на участие и не назначает блоки. У старых приглашений, для которых исходный токен не сохранён, ссылка не восстанавливается из хеша.


## Оформление Mednet Kit (отдельная ветка)

Используются `@mednet/tokens@2.0.0` и локальные шрифты из `@mednet/css@2.0.0`. Способ подключения соответствует [инструкции для существующего сайта без React](https://mednet-kit-doc.vercel.app/docs/static): подключены токены и fonts.css, без глобального сброса mednet.css. Цвета, типографика, радиусы и тени берутся из токенов; бизнес-логика и модель не меняются. Логотип и реквизиты института не добавлялись: использование оформления не означает институционального авторства исследования.

```bash
npm ci --ignore-scripts
npm run build:design
npm run check
node tests/browser.cjs
```

Собранные токены, шрифты и лицензии лежат в `static/vendor/mednet/` и входят в Git; Node не требуется на рабочем сервере. Внешних запросов шрифтов из браузера нет. Для скриншотов используются только вымышленные участники во временной базе. [Просмотр экранов](../docs/mednet-preview/README.md).
